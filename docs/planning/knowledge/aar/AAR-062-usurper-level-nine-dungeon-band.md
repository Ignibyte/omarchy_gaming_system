## What happened

The separate Usurper workspace advanced to unadmitted rules, state, and
cartridge v14. It now stores exact v0.20e Level 9 editor records 80–89,
supports draw-free selection across levels one through nine, preserves the
source-order `Random(90)` rejection loop, and initializes normally reachable
Level 9 monsters at source-derived strength 19, defence 9, and 57 HP. Existing
combat, healing, spell, class-special, reward, retreat, and Gnoll poison paths
remain owned by the same deterministic reducer.

Provider-backed workspace-8 play then found defects outside the new game data:
the local adapter kept the pre-mutation screen, the signed presentation exposed
same-label provider and navigation controls, and held Return events could cross
an asynchronous plan replacement. The provider now follows the authenticated
candidate view's screen, Usurper exposes exactly one phase-valid command per
visible choice, and generic trusted button/grid nodes reject activation
auto-repeat. Live keyboard play advanced one revision per activation through
entry, character setup, Main Street, Level 1, Level 9, and a Severe Madman
encounter at 57/57 HP.

The external suite passed all 79 Rust tests, strict Clippy, rustdoc, immutable
source/provenance and privacy checks, every one of seventeen signed screens,
and provider-backed HTTP/QML play. The fixed fifteen-case provider security
corpus passed twice across restart. Final complete security scans of both
repositories reported zero findings, the full 24-stage platform gate passed,
and OpenWiki plus the hand-maintained cartridge architecture were reconciled
before archival.

## Prevention rules captured

| ID | Rule | Why |
|---|---|---|
| `PR-omarchy-gaming-system-exercise-live-shell-across-provider-screen-transitions-001` | A provider-backed local-play smoke must cross multiple authenticated provider phase and screen transitions, not stop after the first confirmed mutation. | First-action success can hide a stale screen that makes every later control inert. |
| `PR-omarchy-gaming-system-render-one-phase-valid-command-per-visible-choice-001` | Render one phase-valid provider command for each visible game choice and reject duplicate visible button labels on every signed screen. | Command/navigation twins confuse users and create a state-skipping surface. |
| `PR-omarchy-gaming-system-reject-activation-autorepeat-across-plan-replacement-001` | Trusted interactive nodes must consume but ignore auto-repeat activation events, with a smoke proving the event cannot cross plan replacement. | Focus can move while a key is held, turning one intended activation into multiple commands. |
| No new ID | Include the exact Compose override in every nested provider-test invocation and update exact metrics parsers with the runtime proof they enforce. | Environment and evidence-contract drift can fail validation after the behavior itself is correct. |

## Effectiveness

Effective. The recalled legacy branch, discarded-RNG, and composite-driver
rules preserved exact Level 9 behavior without broadening provider or platform
authority. More importantly, the real live shell turned user observations into
reproducible state, presentation, and input-lifecycle tests. Exact data and RNG
coverage, unique-label and auto-repeat smoke, the restarted provider corpus,
two sealed zero-finding security reviews, OpenWiki reconciliation, and the green
platform gate jointly validate the slice without Level 10, events, shared
realm, registration, admission, deployment, commit, push, or publication.
